# Extending the THMZ format

A THMZ is a ZIP archive of named entries: XML and JSON documents describing the model,
CSV files holding results, and whatever else a producer chose to put there.

This note records one property of that arrangement, because it decides how a new
capability can be introduced: **entries that a program does not recognise survive when
that program opens and saves the file.** A field can therefore be added to the format and
used in production before any user interface exists for it.

## Why unknown entries survive

Every writer of a THMZ follows the same pattern — read the archive into a map of
name to content, replace only the entries it owns, write the whole map back:

- **LibraryFEMTherm**, in `addToZipFile` (`src/THMZ/ZipModule/ZipModule.cxx`): unzips every
  entry, erases only the names the caller listed as obsolete, replaces the target entry,
  and re-zips the rest.
- **THERM** reads the entire archive into its entry map when a document is opened, updates
  the entries it manages by name, and writes that same map on save. Its removals are all
  aimed at specific known names — stale result files, superseded format variants — never a
  blanket clear.
- **HygroTherm** states the guarantee directly: entries the project class does not touch
  round-trip byte-identical on save. Loading and saving a THMZ is its only input and its
  only output.

The consequence is that the archive carries more than any single program understands, and
each program preserves the remainder on the reader's behalf.

## Rules for adding something

**Add a new entry rather than a new field inside an existing one.** An entry that a
program parses into a model is rewritten from that model on save, so anything added inside
it that the program's parser ignores is discarded — not by intent, but because the
serialised form is regenerated rather than edited. A new entry is never regenerated by
anyone who does not know about it, so it is carried through untouched.

**Check the obsolete-name lists before choosing a name.** Callers pass lists of superseded
entry names to be erased during an update, and format migrations remove names they have
replaced. A new entry whose name appears in one of those lists will be deleted as stale.

**Treat adding a key inside an existing JSON or XML entry as unverified.** Whether unknown
keys survive reserialisation depends on the parsing layer, and has not been established.
Until it is, an entry of its own is the shape that is known to work.

## What this makes possible

A capability can be introduced in stages rather than all at once: define the entry, teach
the mediator to read it, and any producer that writes the entry gains the capability
immediately. Files continue to open in THERM, which passes the new entry through without
understanding it, and a user interface can follow when it is wanted rather than being a
precondition.

The corresponding limit is worth stating alongside it. Only what the format can express
reaches the engine through this path, because the mediator's entire input is the file. A
capability that the engine implements but the format cannot name is unreachable except
from C++ — which is a gap in the format, not in the solver, and is closed by adding an
entry rather than by changing the engine.
